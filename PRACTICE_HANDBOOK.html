01 · Feature brief: Create task

场景

Taskroom 是团队协作工具。协调者在一次演练结束后，需要把后续行动快速分配给同事。目前列表只能查看，无法新增任务。

用户目标：留在当前任务页，创建一条任务，明确责任人和优先级，并立即看到结果。

范围

入口：页面标题右侧的 Create task 按钮。点击后打开居中 modal。手机上使用同一 modal，适应屏幕宽度。

字段 规则 初始值
Task title 必填；trim 后 1–80 个 JavaScript 字符单位；纯空格无效 空
Owner 必填；只允许 seed.js 中三个候选人 空，显示 Choose an owner
Priority 必填；High / Medium / Low Medium
Status 系统自动填写，不显示为可编辑字段 To do

按钮：Cancel / Create task。默认提交按钮可点击，便于学习提交后的 inline validation；保存时禁用并显示 Creating…。

必须覆盖的状态

  1. 初始表单：标题输入框获得焦点。
  2. 错误：空标题、纯空格、81 字符、未选 Owner，在对应字段下显示错误；聚焦第一个错误字段。80 字符合法。UI 不得仅靠 maxlength 阻止你观察超长错误。
  3. 保存中：防重复提交；字段及 Cancel 暂时禁用，并在保存期间阻止 Escape 关闭。
  4. 成功：关闭 modal、新任务出现在第一行、总数更新、Toast 显示 Task created.；焦点回入口。
  5. 保存失败：显示表单级错误、保留输入、恢复按钮、支持重试；不新增行。
  6. Cancel / Escape：未保存就关闭，不新增数据；下次打开是一份干净表单。
  7. 空列表：可创建第一条任务。
  8. 刷新：已保存任务仍在当前浏览器。

不做

编辑 / 删除 / 搜索 / 到期日 / 登录 / 后端 / AI 生成任务 / 权限管理 / 邮件通知。

验收标准

  • AC01：所有入口和字段使用既有 DS；没有复制一套按钮或表单组件。
  • AC02：合法输入能创建，标题去除首尾空格，状态为 To do。
  • AC03：非法输入显示 inline error，无新增数据。
  • AC04：保存中多次点击只产生一条记录。
  • AC05：失败保留输入并可重试成功。
  • AC06：取消 / Escape 无保存；再次打开无旧输入与错误。
  • AC07：创建成功后列表、数量、空状态同步更新；刷新保持数据。
  • AC08：键盘可完成全流程；焦点不离开 modal；关闭后回入口。
  • AC09：390px 与 1440px 宽度可操作，没有横向溢出。
  • AC10：原列表、组件库、Reset demo data / Show empty state 均继续可用。

02 · Design System 使用说明

先打开 /components.html，再读源码。这里的“调用”就是导入真实组件并按其 API 使用。

组件来源

import { Button, Field, Dialog, Toast, Banner } from './design-system/components.js';

上面的相对路径适用于 src/ 下的文件；若功能放进 src/features/，需改成 ../design-system/components.js。

组件 参数 返回 使用方式
Button label, variant: primary/secondary/ghost, onClick, type, disabled button DOM append 到容器；提交按钮用 type: submit
Field id, label, kind: input/select, type, options, required, hint {root, control, setError} append root；通过 control.value 取值
Dialog title, onClose {root, body, footer, open, close} 把 form 放 body，按钮放 form 内；open 调用 showModal
Badge label, tone: default/success/warning span DOM 优先级或状态
Toast message 字符串 DOM Toast('Task created.')
Banner message 字符串 DOM 表单级错误，role=alert

示例：复用一个字段

const title = Field({
  id: 'task-title', label: 'Task title', required: true,
  hint: 'Use 80 characters or fewer.'
});
form.append(title.root);
title.setError('Enter a task title.');
title.control.focus();

这是 API 示例，不是完成后的功能。完整交互需要你在练习阶段连接。

Tokens

类型 既有值 / 变量 规则
主色 --color-primary 主要操作和焦点
文字 --color-text / --color-muted 复用，不在 feature 中随意加灰色
错误 --color-danger / --color-danger-soft 同时使用文字说明，不只变红
间距 --space-1…7：4/8/12/16/24/32/48px 新布局优先使用现有变量
圆角 --radius-sm/md/lg 6/10/16px
字号 --font-sm/md/lg/title 13/15/20/32px

组合约束

  • 一个界面只保留一个主要提交动作；Cancel 用 secondary。
  • 用 form 的 submit 事件，支持 Enter；设置 form.noValidate=true，统一走已有数据层校验，以呈现一致的 inline error。
  • 推荐在 dialog.body 中放整个 form，把 .ds-dialog-actions 容器也放进 form，避免提交按钮脱离 form。
  • 每次打开可创建新 dialog；关闭后 root.remove()，避免 DOM 累积。
  • 原生 dialog 提供 modal 基础行为；仍需验收 Tab、Shift+Tab、Escape 和焦点回归。
  • 保存中在 dialog.root 的 cancel 事件中 preventDefault()；完成或失败后恢复正常关闭行为。
  • 新样式加到 app.css 的功能区域；只有可复用能力才修改组件库，并同步 showcase。

已有数据能力

const service = createTaskService({storage: localStorage});
service.listTasks(); // 同步返回任务数组；读取失败会抛异常

service.reset(); // 移除保存数据，下次读取回到 3 条 seed

createTask 的内部步骤：校验 → 模拟 500ms 延迟 → 可选故障 → 构造任务 → 写 localStorage → 返回。校验错误有 error.fields；保存错误用表单级 Banner。UI 应捕获错误。

记录：{id, title, owner, priority, status, createdAt}。新任务 prepend 到数组，status 固定 To do。

可重复的失败演练

在新 feature 中加入仅用于练习的故障入口：

// 由 Claude 在实现阶段接入。基础包尚无提交 UI。
let failNext = new URLSearchParams(location.search).has('failSave');
// 每次调用前：
const simulateFailure = failNext;
failNext = false;
await service.createTask(draft, { simulateFailure });

用 http://localhost:5173/?failSave=1 打开。输入合法内容，第一次提交失败，第二次重试成功。failNext 在功能挂载时初始化，不能每次 submit 都重新读取 URL，否则无法重试成功。保持页面不刷新进行重试。

空状态与重置

列表底部已有 Show empty state 和 Reset demo data。前者写入空数组，后者删除练习数据恢复种子。使用同一浏览器和同一网址端口。

构建和部署

npm run build 只复制 index.html、components.html、src 到 dist，不发布 docs、outputs、测试或 CLAUDE.md。所有资源使用相对路径，兼容 GitHub Pages 的仓库子路径。

这不是 React 工程，没有 bundler、服务器 API 或数据库。此选择减少初学者环境问题；公司练习时用公司真实栈替换，不要直接搬入生产仓库。

docs/05-release-runbook.md

05 · GitHub / CI / Release runbook

本练习：GitHub 保存源码 → PR 运行 CI → 合并 main → 手动运行 Pages workflow → URL 验证。Merge 不会自动部署。 无 PR 在线预览；PR 的 CI 产物可下载后本地查看。

A. 首次上传

  1. GitHub 网页创建仓库 ai-design-foundation。建议用个人练习 public 仓库，便于使用 Pages；所有内容保持虚构。不要自动添加 README、license、.gitignore，确保仓库为空。
  2. 本地项目根目录（package.json 所在处）打开终端。先 git status；如果显示已是其他仓库的一部分，停止并确认目录，不要嵌套初始化。
  3. 若未初始化，逐条执行：
git init -b main
git add .
git status
git commit -m "chore: add Taskroom design practice foundation"

首次 commit 可能要求 user.name / user.email。使用你自己的 GitHub 资料；可用 GitHub Settings → Emails 显示的 noreply 邮箱。由你填写真实值。

  1. 在 GitHub 新仓库页面复制实际 HTTPS remote。运行下列命令前，把 YOUR_GITHUB_USERNAME 替换成实际账号；仓库名不同也要对应修改：
git remote add origin https://github.com/YOUR_GITHUB_USERNAME/ai-design-foundation.git
git push -u origin main

如果 origin 已存在，先 git remote -v，不要重复添加或盲目覆盖。

认证优先用 GitHub 支持的浏览器登录 / credential manager 或 GitHub Desktop。GitHub 账号密码不是 HTTPS Git 的有效密码；不要把 token 发给 Claude 或写进文件。也可以使用你已经配置好的 SSH。

  1. GitHub → Actions → CI，确认 verify 运行成功。无需 npm install，因为没有第三方依赖。

B. 分支与 PR

git switch main
git pull --ff-only
git switch -c feat/create-task

实现、检查后提交并 push。只在确认 diff 属于本次功能后暂存文件；不要把不相关变更一起提交。

git status
git diff
git add src tests outputs
git commit -m "feat: create tasks from the task list"
git push -u origin feat/create-task

若有其他应提交的文件，检查后逐个 add。GitHub → Pull requests → New pull request → base main / compare feat/create-task。填写模板，检查 CI。单人练习自己 Review 不等于独立审查；公司按其规则执行。

CI 包含语法、数据测试、构建，不自动验收所有 UI。产物名 app-build；如果下载 PR 产物，可解压到单独文件夹，用本机静态服务器查看，别覆盖工作目录。

C. 手动发布

  1. 验收通过后在 GitHub 合并 PR。为方便回退，选择 Create a merge commit。
  2. 仓库 Settings → Pages → Build and deployment → Source 选 GitHub Actions。
  3. Actions → Release to Pages → Run workflow，Branch 选 main。
  4. workflow 在 main 上重新运行 check / test / build，上传 dist，然后 deploy。
  5. 在成功的 deploy job / environment 中打开实际 URL。通常是 https://账号.github.io/仓库名/，以实际返回地址为准。
  6. 执行 Q18，记录到 outputs/04-release-log.md。日志修改可单独提文档 PR；不必为了记录日志重复部署应用。

workflow 只允许 main；其他分支触发会跳过。没有设置 required reviewer 时手动点 Run 就是发布触发点；组织若配置 environment 审批，还需按其要求完成。

GitHub Release / tag 是版本记录，不会因创建它就自动部署本项目。

D. 回退：保留历史，重新部署

此站点没有 feature flag，练习用 revert 恢复旧代码。不删 localStorage，已有任务数据可以继续保留。

  1. 从 PR 页面找到实际 feature merge commit。记下 SHA，不使用下方占位符原样运行。
  2. 确认工作区干净，更新 main，创建 revert/create-task 分支。
  3. 若确实使用了 merge commit：git revert -m 1 ACTUAL_FEATURE_MERGE_SHA。
  4. 若使用 squash merge，应对单个 squash commit 执行 git revert ACTUAL_SQUASH_SHA，不用 -m 1。不要凭猜测选命令。
  5. 运行 check / test / build，push 新分支，创建 PR，审查后合并。
  6. 再手动运行 main 的 Release to Pages。单纯 revert / merge 还没改变线上。
  7. 正式网址刷新，确认创建入口消失、任务列表正常。
  8. 恢复 feature：从更新后的 main 创建恢复分支，对上面生成的“回退内容 commit”做普通 git revert ACTUAL_REVERT_COMMIT_SHA，检查、PR、合并、再部署。不要误用包含它的 PR merge commit。

遇到冲突，让 Claude 先解释冲突和目标行为再修复，检查通过后继续。不要 force-push、reset --hard 或删除 main。

E. 常见问题

现象 先检查
git push 失败 remote 是否正确、GitHub 认证、仓库权限；不要改应用代码
CI 不出现 .github/workflows 是否上传、Actions 是否启用
Pages 404 发布来源是否 GitHub Actions；deploy 是否成功；是否打开仓库子路径
Run workflow 不出现 pages.yml 是否已在 main；是否有 workflow_dispatch
deploy 权限失败 pages:write、id-token:write、组织策略、github-pages 环境限制
线上仍旧界面 最近部署 SHA 是否为 feature 合并之后；是否实际点过手动发布
本地新增数据线上没有 localStorage 按 origin 隔离，预期行为
